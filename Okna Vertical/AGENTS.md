# Правила проекта

## Запрет принудительных переносов

- Никогда и нигде не использовать HTML-тег `br` в любой форме и регистре: в страницах, шаблонах, компонентах, данных, JS-строках и сгенерированной разметке.
- Текст должен переноситься естественно по ширине блока. Не заменять `br` принудительными переносами через CSS или JavaScript.
- Перед сдачей проверять исходники и production-сборку на отсутствие тегов `br`; устранять их в источнике, чтобы сборка не возвращала их.

## Форматирование CSS

- Все исходные CSS вне `dist` оформлять для удобного редактирования: свойства и закрывающие скобки на отдельных строках, отступы настоящими табами. Внутри медиазапросов добавлять один уровень отступа. Не писать правила CSS одной строкой.
- Форматировать новые и изменённые исходные стили перед сдачей с настройками `.prettierrc.json` и `.editorconfig`. Сборочные CSS в `dist` вручную не форматировать.

## Единые фотографии товаров

- На всех подстраницах соответствующие `.home-hero-card img`, `.home-product-card img` и варианты выбора товара в квизе должны использовать одну и ту же фотографию.
- Источник фотографии — данные hero-карточки; при замене синхронизировать карточку товара, квиз и изображения в их модальных окнах через общий генератор компонентов.
- Главная страница исключена из этого правила и сохраняет собственные фотографии блоков.

## Изображения

- Для каждой загружаемой, добавляемой или заменяемой картинки проверять её фактический максимальный размер отображения.
- Уменьшать любую картинку до этого размера с запасом около 10%, а не хранить исходник значительно крупнее.
- Это правило распространяется на все изображения проекта: фото, баннеры, карточки, фоновые изображения, изображения квиза и интерфейсную графику.
- После оптимизации проверять вес файла, качество, пропорции, ссылки и отсутствие битых ассетов.

## Классы секций и типовые блоки

- Каждой секции подстраницы давать один уникальный класс формата `страница-блок` в латинице и kebab-case, например `apartment-hero`, `apartment-price`, `apartment-reviews`.
- Сохранять общие классы типовых блоков: основной шаблон и оформление берутся с главной страницы.
- Не копировать общие стили под каждую страницу и не создавать уникальные классы для каждого вложенного элемента. Класс страницы нужен для идентификации секции и только необходимых отличий.
- Классы должны присутствовать в исходном HTML и сохраняться при production-сборке.

## Универсальные компоненты

- На всех страницах кнопки действий должны открывать релевантный попап, а не переводить к якорю секции. Единственное исключение — «Смотреть примеры работ»: это всегда ссылка-якорь к блоку кейсов текущей страницы, а при отсутствии кейсов — `/portfolio/#works`. Она никогда не открывает попап и не имеет атрибутов `data-package-*`. Передавать тему, описание, подпись отправки и тип вложения через `data-package-*`. Для проверки сметы попап должен позволять прикрепить смету. Навигационные ссылки меню остаются ссылками.

- Типовые блоки страниц собирать из `components/*.html` и данных `seo-pages/components/*.js` через `scripts/components.mjs`.
- Для новой страницы менять данные, `prefix` и `order`; не копировать разметку блока, не извлекать его из главной регулярными выражениями и не делать замены текста в HTML главной.
- Поведение компонентов привязывать к общим классам и `data-component`, а не к имени страницы. Настройки квиза, калькулятора и монтажных вкладок передавать через данные блока.
- Управляемые области `index.html` с комментариями `component:...` обновляются при сборке; править их в шаблонах и данных.
- После изменения компонентов запускать `npm run build` и `npm run check:components`. Подробности — `components/readme.md`.
