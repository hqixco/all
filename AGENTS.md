# Общие правила для всех проектов

Эти правила обязательны для всех текущих и будущих проектов внутри общей папки.

## Имена файлов и ассетов

- Использовать только латиницу в нижнем регистре, цифры и дефисы (`kebab-case`).
- Не использовать кириллицу, пробелы, заглавные буквы, скобки и случайные суффиксы.
- Имена должны быть короткими и описывать назначение: `logo-vert-os.png`, `hero-house.webp`.
- При добавлении или замене файла сразу переименовывать его и обновлять все ссылки в HTML, CSS, JS, конфигурациях, sitemap, SEO-разметке и JSON.
- Перед сдачей искать старое имя по всему проекту и проверять существование каждого ассета.

## Стабильные имена файлов сборки

- Никогда не добавлять к именам CSS, JS, изображений, шрифтов и любых других ассетов content hash, UUID, timestamp, случайные строки, номера сборок и прочие уникальные суффиксы.
- Имена файлов должны быть постоянными, короткими и описательными: `main.css`, `main.js`, `hero-house.webp`.
- Для production-сборки обязательно отключать генерацию хешей в именах entry-файлов, chunks и assets. После сборки проверять содержимое `dist` и ссылки в HTML, CSS, JS, manifest, sitemap, SEO-разметке и JSON.
- При изменении содержимого сохранять прежнее стабильное имя файла, если назначение ассета не изменилось.
## Изображения

- Тяжёлые изображения обязательно оптимизировать до публикации.
- Для фотографий использовать WebP или AVIF; PNG оставлять для прозрачности, логотипов и интерфейсной графики.
- Для фото использовать WebP quality примерно 78–85, PNG сжимать lossless или индексированной палитрой.
- Размер подбирать под фактический размер отображения: обычно 1.25–1.5× от максимального CSS-размера для запаса и Retina.
- Не хранить изображения в 2–4 раза крупнее нужного; для адаптивных размеров использовать `srcset` или несколько вариантов.
- Ориентир веса: обычное фото до 200–300 КБ, небольшая графика до 100–150 КБ. Больший вес допустим только для крупных hero-изображений.
- Проверять пропорции, `width`, `height`, `alt`, качество и отсутствие битых ссылок.

## Адаптивная вёрстка

- Никогда не использовать `min-width` в медиазапросах. Для адаптации по ширине использовать только `max-width`: базовые стили для больших экранов, затем переопределения для меньших.

## CSS-каскад и исправления стилей

- Не использовать `!important` для устранения конфликтов и перебивания стилей.
- При конфликте сначала находить истинную причину: дублирующиеся правила, неверный порядок подключения, избыточную специфичность или слишком широкие селекторы.
- Устранять конфликт в источнике и оставлять один понятный источник истины для каждого адаптивного компонента.
- Не наращивать специфичность селекторов для маскировки проблем каскада.

## Иконки

- Никогда не использовать текстовые символы, буквы, Unicode-знаки и emoji в качестве иконок, в том числе через CSS-свойство `content`.
- Для иконок использовать только SVG или подходящие графические ассеты.
- Декоративным SVG задавать `aria-hidden="true"`; значимым иконкам предоставлять доступное текстовое описание.


## Совместимость со старым Safari

- Все сайты и production-сборки обязательно поддерживать в старом Safari, ориентир — Safari 13 и новее.
- В конфигурации сборщика задавать CSS target не новее `safari13` (для Vite: `build.cssTarget: "safari13"`) или эквивалентную настройку совместимости.
- После production-сборки проверять итоговый CSS: медиазапросы должны сохраняться в классическом виде `@media (max-width: ...)`. Не допускать преобразования в range syntax `@media (width <= ...)`, поскольку старый Safari такие правила отбрасывает.
- Не использовать без совместимого fallback возможности CSS и JavaScript, которые не поддерживаются Safari 13. Проверять именно собранные файлы из `dist`, а не только исходники.
## Проверка

- Проверить старые и ненормальные имена файлов и ссылки на ассеты.
- Запустить production-сборку.
- Не менять пользовательские правки вне текущей задачи.

## Статическая разметка

- Весь постоянный контент страниц должен находиться в HTML при первой загрузке: секции, карточки, тексты, изображения, формы, модальные окна и базовое состояние интерактивных блоков.
- Не создавать, заменять и перестраивать постоянную разметку через JavaScript, в том числе через innerHTML, insertAdjacentHTML и createElement.
- JavaScript использовать только для поведения после действий пользователя: переключения состояний, галерей, квизов, меню и отправки форм. Базовое содержимое должно оставаться доступным без JavaScript.
- При изменении страницы править HTML напрямую и удалять устаревший JS-рендер, чтобы не было двух источников истины.

## Запрет принудительных переносов

- Никогда и нигде не использовать HTML-тег br в любой форме и регистре: в страницах, шаблонах, компонентах, данных, JS-строках и сгенерированной разметке.
- Текст должен переноситься естественно по ширине блока. Не заменять br принудительными переносами через CSS или JavaScript.
- Перед сдачей проверять исходники и production-сборку на отсутствие тегов br; устранять их в источнике, чтобы сборка не возвращала их.
